# Architecture

This document is the narrative map of how `terraform-aws-messaging` fits
together. It's meant to answer "why is it shaped this way" faster than
reading every `.tf` file. Mechanical variable/output tables live in each
module's own README (generated by `terraform-docs`, see below) — this
file doesn't duplicate those.

**Keeping this current**: a `PostToolUse` hook (`.claude/settings.json`)
reminds Claude to check this file whenever a root or `modules/**/*.tf`
file changes. Humans get the same reminder implicitly via this note. If a
change adds/removes a resource, a variable that changes control flow, or
an IAM relationship, this file should change in the same commit/PR.

## Module graph

```
root (main.tf, iam.tf, s3_offload.tf, locals.tf)
├── module.topic          → modules/sns        (count = var.create_topic ? 1 : 0)
├── module.dlq[k]         → modules/sqs        (for_each = local.dlq_queues)
├── module.queues[k]      → modules/sqs        (for_each = local.queues)
└── module.payload_bucket → modules/s3         (count = local.enable_large_payload_offload ? 1 : 0)
```

`modules/sns`, `modules/sqs`, and `modules/s3` are each a single-resource
wrapper around one AWS primitive plus its close companions (e.g.
`modules/s3` also owns the bucket's public-access-block, SSE, and
lifecycle-expiration resources). None of the three know about messaging
semantics — naming, FIFO suffixing, and precondition validation only.
All cross-resource wiring (redrive policies, topic subscriptions,
IAM trust) happens at the root. Why nested submodules instead of one flat
module: [ADR 0001](decisions/0001-nested-submodule-split.md).

## Data flow

```
             (optional)
producer ──publish──▶ SNS topic ──subscribe──▶ SQS queue ──consume──▶ consumer
                                       │
                                       ├─(create_dlq)──▶ DLQ  (redrive after max_receive_count)
                                       │
                                       └─(enable_large_payload_offload)
                                              │
                                     producer ─PutObject─▶ S3 bucket ─GetObject─▶ consumer
                                     (pointer message carries the S3 key; SQS/SNS
                                      never sees payload bytes over 256KB)
```

A queue can also skip the topic entirely (`subscribe_to_topic = false`)
for direct-send-only use, e.g. the `audit` queue in the usage examples.

## Settings resolution (`locals.tf`)

Every queue-level numeric/duration setting (`visibility_timeout_seconds`,
`message_retention_seconds`, `max_message_size`, `delay_seconds`,
`receive_wait_time_seconds`, `max_receive_count`) is resolved exactly
once, in `locals.queues`, via `coalesce(queue-specific value,
var.default_queue_settings.<field>)`. Every resource and IAM policy
downstream reads from `local.queues`, never from `var.queues` directly —
so a new setting only needs the coalesce added in one place, and nothing
else changes. The same pattern resolves each queue's final name
(`coalesce(q.name_override, "${var.name_prefix}-${k}")`).

## IAM model

There is no blanket transmitter/receiver role for the module. Each queue
independently opts in to its own tx (send) and/or rx (consume) role via
`create_tx_role`/`create_rx_role`; the topic only ever gets a tx
(publish) role, since consuming happens through a subscribed queue's own
rx role, not the topic. Why per-resource roles instead of one shared
pair: [ADR 0002](decisions/0002-per-queue-iam-roles.md).

Each tx/rx permission set is always materialized as a standalone,
reusable `aws_iam_policy` first (`local.queue_tx_policy` /
`local.queue_rx_policy` in `locals.tf`) — present whenever the role flag
*or* the bare-policy flag (`create_tx_policy`/`create_rx_policy`) is set.
The role, when requested, is just that same policy attached to an
assumable `aws_iam_role`. This lets a caller with static credentials
(no `sts:AssumeRole` available, e.g. an IAM user's access keys) attach
the policy ARN directly instead.

A role's trust policy defaults to the AWS account root when no
`tx_principal_arns`/`rx_principal_arns` is supplied — this is a deferred
grant, not an open door, since IAM is still default-deny until a specific
principal is separately granted `sts:AssumeRole` on the role's ARN. Why:
[ADR 0004](decisions/0004-trust-policy-fallback-to-account-root.md).

```
queue "orders" (create_tx_role=true, create_rx_role=true)
├── aws_iam_policy.queue_tx["orders"]   sqs:SendMessage → orders queue
│                                       (+ s3:PutObject → payload bucket, if offload enabled)
├── aws_iam_role.queue_tx["orders"]     trusts tx_principal_arns (or account root)
├── aws_iam_policy.queue_rx["orders"]   sqs:ReceiveMessage/DeleteMessage/... → orders queue
│                                       (+ sqs:ReceiveMessage → orders-dlq, if create_dlq)
│                                       (+ s3:GetObject → payload bucket, if offload enabled)
└── aws_iam_role.queue_rx["orders"]     trusts rx_principal_arns (or account root)
```

## Large-payload (S3) offload

`modules/s3` is a generic, messaging-agnostic bucket module (blocked
public access, SSE-KMS, lifecycle expiration). It's created at the root
only when at least one queue sets `enable_large_payload_offload = true`.
What ties it to this repo isn't the bucket — it's the IAM: a queue that
opts in gets `s3:PutObject` (tx) / `s3:GetObject` (rx) scoped to this one
bucket, added as an extra statement in that queue's own tx/rx policy.
This module does **not** decide when a payload is "too big" or perform
the offload itself — that logic (hash-check size, PUT-then-publish-a-
pointer) is the producer/consumer application's job. Why bundled here
instead of a separate artifact-store repo:
[ADR 0003](decisions/0003-bundle-s3-offload-bucket.md).

## Generated reference docs

A single `.terraform-docs.yml` at the repo root drives every module's
mechanical input/output table — there's one shared config, not one per
module. Each module README (root, `modules/sns`, `modules/sqs`,
`modules/s3`) has a `<!-- BEGIN_TF_DOCS -->` / `<!-- END_TF_DOCS -->`
block that `terraform-docs` injects into. Regenerate after changing any
`variable`/`output` block, running from the repo root so the `--config`
path resolves:

```bash
for d in . modules/sns modules/sqs modules/s3; do
  terraform-docs markdown table --config .terraform-docs.yml --output-file README.md --output-mode inject "$d"
done
```
